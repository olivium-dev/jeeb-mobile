### 4.2 The #577 `offer_lost` defect — found, then closed

This is the single most important open-then-closed backend item.

**What the verifier found** (`SP/resume-wave/backend/p02-gateway/VERIFY.md` §H, on head `be413069`, verdict FAIL): the gateway's own producer emitted `OfferLostDeepLink(offerId) => "jeeb://offers/{offerId}"` (`OfferPushNotifier.cs:132`), stored verbatim as the row's `payload.deepLink`. The branch's new fail-closed reader `ValidateExplicitLink` rejected exactly that shape — it is in neither the gateway allow-list nor mobile's 16 route regexes — and threw. Result: `GET /v1/notifications` answered **502 for that user's entire page**, for any jeeber who had ever lost an offer. Reproduced in an isolated clone (`verify2/offer-lost-repro.log`). No test covered it, because neither captured fixture contains an `offer_lost` row.

**The batch-2 repair landed** in `ca7d28c2` (12 files, +277/−80): `ValidateExplicitLink` became `MatchExplicitLink` — returns the link when well-formed *and* in the grammar, returns `null` when well-formed but naming no route, still **throws** for a malformed envelope. An unmatched link nulls that one row's `deepLink`; the projection falls back to inbox-root semantics and the row keeps its `ref`. Send side: `OfferLostDeepLink` and the `deepLinkOverride` parameter are deleted. **No backfill** (decision D2). New test `P02OfferLostInboxRoundTripTests` takes the payload from the **real** producer and drives the real route, including the pre-fix shape → **200**.

**But note the verification gap.** Both gateway verifier agents died on the Fable limit; the run records `p02-offer-lost=unresolved` and `p01-openapi-g13=unresolved`. `ca7d28c2` and `d906eedd` carry the executor's measurements and green hosted CI, and **no independent second-party verification**.
