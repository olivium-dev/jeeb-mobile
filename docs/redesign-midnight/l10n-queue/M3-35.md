# M3-35 · biometric-unlock (`/lock`) — l10n queue

**NO NEW KEYS REQUESTED.** The restyle mounts only keys that already exist in
both `app_en.arb` and `app_ar.arb`. Two items for the l10n lane, both
corrections to existing strings — filed here because this queue is that lane's
inbox, not because a key is missing.

## 1. `biometricLockPrompting` is now RENDERED (was dead copy)

`"Waiting for biometrics…"` / `"بانتظار التحقق…"` existed in both arbs and was
never mounted. M3-35 renders it as the loading state (the in-flight line under
the body, R7's `registrationOtpVerifying` precedent). **No change needed** —
recorded so the lane does not prune it as unused.

## 2. `biometricLockFailure` names two affordances the screen does not have

Current: `"Biometric check failed. Try again or use your PIN."`
(ar: `"تعذّر التحقق. حاول مرة أخرى أو استخدم الرمز السرّي."`)

The screen's only fallback is `biometric_unlock_use_password_link` —
`"Use password instead"` — which routes to **`/register`**, the phone-OTP
re-auth entry. The email/password funnel died in JEBV4-199 (Q-044) and no PIN
entry surface exists anywhere in the app (`SharedPrefsPinRepository` only feeds
`BiometricLockCubit.evaluate()`'s `canChallenge` check). So the failure copy
offers a PIN that cannot be entered, and the link offers a password that cannot
be typed.

Proposed (owner call, NOT applied — copy is not this lane's to change):
- `biometricLockFailure` → "Biometric check failed. Try again, or sign in with
  your phone number."
- `biometricUnlockUsePasswordLink` → "Use your phone number instead"

## 3. Orphan keys, flagged not touched

`biometricLockTitle` and `biometricLockUsePin` have **zero** call sites in
`lib/` (the screen uses `biometricUnlockTitle` and
`biometricUnlockUsePasswordLink`). `biometricLockTitle` is a verbatim duplicate
of `biometricUnlockTitle` in both locales. Candidates for the l10n lane's dead-key
sweep; left in place here.
