# l10n queue — M3-36 jeeber pending offers

One new string. It exists because the Midnight §2.7 state family needs a
**headline** where the OMDS surface it replaces needed none (`OmdsLoadingState`
took no copy at all).

Verified against `lib/l10n/app_en.arb` / `app_ar.arb` on 2026-08-04.

| Key | EN | AR |
|---|---|---|
| `pendingOffersLoadingHeadline` | `Loading your offers` | `جارٍ تحميل عروضك` |

## `pendingOffersLoadingHeadline`

Member of the shipped "Loading your …" family — `activeDeliveryLoadingHeadline`,
`earningsLoadingHeadline`, `orderHistoryLoadingHeadline`,
`customerProfileLoadingHeadline`, `walletActivityLoadingHeadline`,
`txnDetailLoadingHeadline`, `savedAddressesLoadingHeadline`.

Call site: `_buildBody`'s loading branch in
`lib/features/jeeber_pending_offers/presentation/jeeber_pending_offers_screen.dart`.

### Where it renders from meanwhile

`l10n.pendingOffersTitle` ("Pending offers"), tagged
`TODO(midnight): l10n-queued`. That **violates the header-band rule**
(`orderHistoryLoadingHeadline`'s own ARB description: a loading headline must
not repeat the header band's own title) and the M3-36 loading capture shows the
duplication plainly — the bar reads "Pending offers" and so does the block.
It is still the right stand-in: the only other candidate,
`pendingOffersEmptyTitle` ("No pending offers"), is **false while the read is in
flight**, and inventing an inline copy holder in a file that ships none would be
new machinery for a temporary string.

Note the already-shipped twin of this list — the R16 feed's Pending-Response
sub-tab, `jeeber_feed_tab_view.dart:_pendingBody` — passes
`pendingOffersEmptyTitle` as its loading headline, i.e. it renders "No pending
offers" while loading. **That is a copy defect on a shipped screen**, not a
precedent; when this key lands, both call sites should take it.

## Deliberately NOT queued

- **An error headline.** `offersLoadErrorTitle` ("Couldn't load offers" /
  "تعذّر تحميل العروض") already exists in both locales and says exactly what this
  block needs. Reused, not duplicated.
- **An error body.** The pre-Midnight `OmdsErrorState` rendered
  `offerSubmissionErrorGeneric` — *"Something went wrong sending your offer.
  Please try again."* — as the body of a **load** failure, which is the wrong
  sentence (this screen never sends anything). The §2.7 block drops it: the
  existing correct headline plus the "Try again" pill carry the state with no
  new key and no wrong copy. `offerSubmissionErrorGeneric` itself stays — it is
  still the offer-composer's string.
- **An "Awaiting customer decision" key.** Still absent (JM-047 owns it);
  `PendingOfferRow._AwaitingLabel` keeps reusing `jeeberFeedStatusPending` as it
  has since w2. Unchanged by this row.
